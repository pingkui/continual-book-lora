  - TPU 上 `eigh` 默认按 bf16 精度计算，必须设成 highest。
  - 有 massive activation 的 `down_proj` 层，fp32 的 Gram 矩阵 eigh 会坏掉，需要改用 float64。
  - n≈4096 时 TPU `eigh` 编译要几十分钟，不可用。主机上 numpy 的 eigh 也很慢。现在改用主机上的 torch/MKL（4096 规模 3.9 s），并且必须设 `TORCH_DEVICE_BACKEND_AUTOLOAD=0`，不然 torch_tpu 会占住 TPU。
  - 通用文本误差的评测行，应该取维基百科流的第 300–340 条。
  - 结果要在子空间更新之前保存。

## 1. 目标与理由

- **最终目标**：在 Kaggle TPU v5e-8 上跑 7B 的连续注入实验（书 2→3→4），评测与 Kaggle GPU 版（`lab/train_cl.py`）完全一致。
- **Colab 的角色**：Colab v5e-1 用来开发和验证 1.5B 版本。7B 在 v5e-1（16 GB）上装不下，只能在 Kaggle v5e-8（8 块芯片，共 128 GB）上跑。
- **为什么换 JAX**（下面的数字是估计，在第 2 阶段实测）：

  | 问题 | 现状 | 预期 |
  |---|---|---|
  | 训练速度 | PyTorch + torch_tpu 每步约 1.9 s，TPU 算力只用到约 6% | 每步 0.3–0.5 s |
  | 考试 | HF `generate` 每生成一个词元都要和主机同步一次 | 整个生成循环编译好一次跑完，720 题估计 1 分钟以内 |
  | 保护子空间 | eigh/svd 在 TPU 上不支持，只能在主机 CPU 上算 | `jnp.linalg.eigh` 可以直接在 TPU 上算 |
  | 多核 / 7B | torch_xla 在 Kaggle TPU 上难装、难调 | JAX 内置分片，1.5B 代码加上分片就能用于 7B |
  | 正确性 | torch_tpu 的 sdpa 反向传播算错了 q/k/v 的梯度，见 `tpu/diag.py` | 自己实现的模型，每一步都能和 PyTorch 逐项核对 |

## 3. 设计原则

- **纯 JAX + optax**，不依赖 Flax/NNX：参数用普通 pytree，前向就是纯函数，方便分片，也方便和 PyTorch 逐层对照。optax 在 Colab 上已预装。
- **只换模型和训练，其余照搬**：分词用 HF tokenizer；出题、评分、保留率用 `lab/factlab.py`；数据目录格式（v6）不变。
- **结果文件格式与 GPU 版一致**（`res["runs"][name]["stages"][...]`），保存每道题的原始回答，和 Kaggle 结果放在一起就能直接比较。
- **形状固定**：训练长度按档补齐（例如 64/128），提示长度 80，新生成 40 个词元，批量固定。每一档只编译一次。
- **语义与 GPU 版对齐**：
  - LoRA r=16，alpha=32，dropout 0.05，目标是全部 7 类线性层，LoRA 参数用 fp32；
  - AdamW，学习率 2e-4，前 20 步预热，然后线性衰减到 5%，梯度裁剪 1.0；
  - 有效批量 32 = 4 个微批 × 8 行，损失按微批平均后再平均，与 GPU 的梯度累积一致；
  - 每步优化之后做投影 `A -= (A Q) Qᵀ`；
  - 每学完一本书，把 LoRA 增量加到 fp32 主权重上，再转成 bf16。
- **一套代码跑 1.5B 和 7B**：模型尺寸从 HF 的 `config.json` 读取；分片方式由一个 mesh 参数控制，单芯片时 mesh 就是 1 个设备。

## 4. 代码结构（`tpu/jax/`）

| 文件 | 内容 |
|---|---|
| `qwen.py` | 读取 safetensors 权重，实现 Qwen2 前向（RMSNorm、RoPE θ=1e6、带偏置的 GQA 注意力、SwiGLU），可选返回各线性层的输入，供记录子空间用 |
| `lora.py` | LoRA 参数初始化、前向时叠加增量、投影、合并到主权重 |
| `train.py` | 用 jit 编译整个训练步：微批累积、AdamW、裁剪、投影 |
| `generate.py` | 带 KV 缓存的贪心生成，用 `lax.while_loop` 一次编译，左侧补齐 |
| `subspace.py` | 按掩码和概率抽样各层输入的词元，在 TPU 上做 Gram 矩阵 eigh（失败时退回主机 float64），正交化，SVD |
| `run_cl.py` | 主流程：方案表（A3_frames、A4_gen……）、逐本训练、评测、保存、每本书后保存结果 |
| `tests/` | 各阶段的数值核对脚本 |

## 5. 分阶段计划

每个阶段都有验收标准，不达标就不进入下一阶段。TPU 时间都是估计值，每次开会话前先报预计用时，征得同意后再开。

### 第 0 阶段：环境确认（与第 1–4 阶段并行）
- **Kaggle**：提交一个很小的 TPU v5e-8 探针，打印 JAX/libtpu 版本、设备列表、主机内存、每核可用 HBM，并做一次 bf16 矩阵乘测速。因为排队可能要好几个小时，所以**最先提交**。
- **Colab**：在第 1 阶段的 TPU 会话里顺带记录版本，不单独开会话。
- **验收**：拿到 Kaggle v5e-8 的实际软硬件信息。如果 Kaggle 镜像的 JAX 版本与 Colab 不同，决定是自己安装 `jax[tpu]` 还是适配镜像版本。

### 第 1 阶段：模型前向（本机 CPU + 1 次 TPU）
- 在本机安装 CPU 版 JAX，用 0.5B 的 fp32 模型和 PyTorch 逐层对照。
- **本机内存规则**：只用 0.5B，开内存保护（可用内存低于 1.5 GB 就自动结束），批量要小。
- **TPU（约 15 分钟）**：1.5B bf16 的损失和 CPU 参考值 4.5958 对照（16 行文本，长度 48，与 `diag.py` 的 T1 相同）。
- **验收**：
  - CPU fp32 下，logits 和 PyTorch 的最大差 < 1e-3；
  - TPU bf16 下，损失和参考值相差 < 1%。

### 第 2 阶段：训练一步 + 测速（**决定是否继续的关卡**）
- LoRA、AdamW、裁剪、投影、微批累积。
- **本机检查**：梯度和 PyTorch CPU fp32 的余弦相似度，每类模块都要 > 0.99（相当于 `diag.py` 的 T3）。
- **TPU（约 20 分钟）**：
  - 30 步记忆测试，torch_tpu eager 的结果是 4.61 → 0.06；
  - 测 1.5B 每步的实际用时。
- **关卡**：

  | 每步用时 | 决定 |
  |---|---|
  | ≤ 0.6 s（比现在快 3 倍以上） | 继续 |
  | 0.6–1.0 s | 先找瓶颈，再决定 |
  | > 1.0 s | 停下，向用户汇报 |

### 第 3 阶段：生成（考试）
- 带 KV 缓存的贪心生成，固定提示长度和批量。
- **本机检查**：0.5B fp32 下，20 个提示的输出和 HF `generate` 逐词元完全一致。
- **TPU（约 15 分钟）**：1.5B 跑一遍书 2 的完整考试（720 题），记录用时。
- **验收**：本机完全一致；TPU 上 720 题的考试 ≤ 3 分钟。

### 第 4 阶段：完整管线 + 与 GPU 对照
- 记录子空间、合并主权重、四项评测（正式考题、另一套考题 exam_gen、训练原句检查、通用文本误差），结果每本书保存一次。
- **本机检查**：0.5B，每本书只取几十行，跑书 2→3，确认流程跑通。投影泄漏要和 PyTorch 版同一量级（约 1e-7）。
- **TPU（约 1 小时，待第 2、3 阶段实测后再估）**：A4_gen 种子 1，书 2→3。
- **对照对象**：Kaggle V8 的 `A4_gen_s1`。指标要落在 GPU 三个种子（s0/s1/s2）的范围内：
  - 书 2 保留率；
  - 书 3 知识题；
  - 陷阱题和孪生题；
  - 通用文本误差。
- **验收**：指标落在 GPU 的种子范围内，并记录一个种子跑完书 2→3 的总用时。

### 第 5 阶段：Kaggle TPU v5e-8 + 7B
- **分片**：8 个设备组成一个 mesh。权重按全分片（FSDP）方式拆到 8 个核上，7B 的 bf16 权重约 15 GB，每核约 1.9 GB。数据并行切分批量。LoRA 参数和优化器状态约 0.5 GB，可以复制到每个核，也可以分片。
- **7B 的估算**（Qwen2.5-7B：28 层，隐藏维 3584，前馈维 18944，词表 152k，嵌入不共享）：

  | 部分 | 估算 |
  |---|---|
  | fp32 主权重 | 约 30 GB，放在主机内存里，所以需要先核实 Kaggle 主机内存 |
  | 保护子空间 Q | 7 类模块共约 9 GB（fp32）。需要分片，或者改存 bf16；改存 bf16 要先验证精度是否够用 |
  | KV 缓存 | 批量 48 × 120 词元，约 0.3 GB |

- **步骤**：
  1. 先用 1.5B 在 v5e-8 上跑一次，和 Colab 结果对照，确认分片代码没问题；
  2. 7B 测内存和速度：只训练几十步，再考 1 次；
  3. 7B 正式运行。
- **交付方式**：Kaggle 脚本内核（`enable_tpu`）+ 数据集（代码和 v6 数据）+ 开网络下载权重，或者用 Kaggle Models 里的权重。
- **验收**：7B 跑完书 2→3→4，并得出与 GPU 1.5B 可比的报告。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 实际加速不到 3 倍 | 换 JAX 的收益变小 | 第 2 阶段设了关卡，最多损失 1 天 |
| Kaggle TPU 排队数小时 | 7B 进度被卡 | 第 0 阶段最先提交；7B 任务尽量一次排完、少排几次队 |

| 7B 保护子空间太大 | 显存或内存不够 | 分片存放、改存 bf16（需验证）、调整 n_feat |
| Colab 免费额度用完 | 开发中断 | 本机 CPU 尽量多做；每次只开短会话；结果自动下载；不换账号 |
| 本机内存只有 11.9 GB | 本机检查把机器撑爆 | 只用 0.5B、小批量，并开内存保护 |
